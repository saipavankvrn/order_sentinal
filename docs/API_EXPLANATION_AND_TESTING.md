# OrderFlow Sentinel — API Reference & Testing Guide

> **Target Version**: 1.2.1-live-demo  
> **Base URL**: `http://localhost:8000/api/v1`  
> **Interactive Swagger UI**: `http://localhost:8000/docs`  
> **Alternative ReDoc UI**: `http://localhost:8000/redoc`  
> **Standard Response Format**: All responses are wrapped in `ApiResponse[T]` with `{ "success": bool, "data": T, "message": str }`.

---

## 1. API Architecture & Testing Philosophy

### API Testing vs. Browser Testing
- **API Testing** (via Swagger UI, curl, or Postman) tests the raw HTTP communication, schema validation, database mutations, and status codes in isolation without presentation logic.
- **Browser Testing** (via the React SPA) tests the complete user journey: React state updates, visual progress steppers, deep-linking, pagination slicing, and user interaction feedback.

## 2. Complete Endpoint Catalog

### Category A: Order Management (`/orders`)

#### 1. `GET /api/v1/orders`
- **Purpose**: Paginated listing of orders with multi-parameter filtering.
- **Query Parameters**:
  - `page` (*int*, default 1): Page number.
  - `limit` (*int*, default 20): Items per page.
  - `skip` (*int*, optional): Direct server-side SQL offset.
  - `status` (*string*, optional): Filter by `PENDING`, `PROCESSING`, `DELAYED`, `COMPLETED`, `FAILED`.
  - `search` (*string*, optional): Substring match on `order_id`, `customer_name`, or `product_name`.
  - `is_demo` (*bool*, optional): If `true`, returns only live demo orders; if `false`, returns historical orders.
  - `demo_session_id` (*string*, optional): Isolates orders created under a specific demo session.
- **Used by**: View A (Dashboard Order Table), View D (Session Orders Drawer).
- **Example Response (200 OK)**:
  ```json
  {
    "success": true,
    "data": {
      "total": 513,
      "page": 1,
      "limit": 20,
      "skip": 0,
      "items": [
        {
          "order_id": "ORD-LIVE-7F3A29B1",
          "correlation_id": "corr-7f3a29b1",
          "customer_name": "Sarah Connor",
          "product_sku": "SKU-CYBER-500",
          "order_amount": 299.99,
          "order_status": "COMPLETED",
          "current_stage": "NOTIFICATION",
          "is_demo_order": true,
          "created_at": "2026-10-31T09:20:00Z"
        }
      ]
    },
    "message": "Orders retrieved successfully"
  }
  ```

#### 2. `GET /api/v1/orders/{order_id}`
- **Purpose**: Retrieves single order details by primary key.
- **Used by**: View B (Order Journey Inspection).
- **Errors**: `404 Not Found` if order does not exist.

#### 3. `GET /api/v1/orders/{order_id}/events`
- **Purpose**: Retrieves all sequential telemetry events (`OrderEvent`) for an order.
- **Used by**: View B (7-Stage Progress Stepper & Event Timeline).

### Category B: Failure Incidents (`/incidents`)

#### 1. `GET /api/v1/incidents`
- **Purpose**: Query incidents by `order_id`, `status` (`DETECTED`, `ANALYZING`, `RESOLVING`, `RESOLVED`), or `failure_category`.
- **Query Parameters**: `order_id` (*string*), `status` (*string*), `failure_category` (*string*).
- **Used by**: View B (Incident Cards) and View C (Approvals Incident Context).

#### 2. `GET /api/v1/incidents/{incident_id}`
- **Purpose**: Retrieve full incident record including linked order and retry count.

---

### Category C: Advisory Root Cause Analysis (`/rca`)

#### 1. `GET /api/v1/rca/incident/{incident_id}`
- **Purpose**: Retrieves structured advisory RCA report generated by Gemini or deterministic fallback.
- **Used by**: View B (RCA Diagnosis Card).
- **Example Response**:
  ```json
  {
    "success": true,
    "data": {
      "rca_id": "RCA-4A2BC910",
      "incident_id": "INC-7F3A29B1",
      "failure_category": "API_ERROR",
      "affected_service": "payment_service",
      "probable_root_cause": "Downstream payment gateway returned HTTP 503 Service Unavailable.",
      "evidence_strength": "HIGH",
      "recommended_action": "RETRY_WITH_BACKOFF",
      "risk_level": "LOW",
      "model_source": "gemini-flash-latest",
      "explanation": "Transient network failure observed. Safe to retry with exponential backoff and idempotency guard."
    },
    "message": "RCA report retrieved"
  }
  ```

### Category D: Self-Healing Resolutions (`/resolutions`)

#### 1. `POST /api/v1/resolutions/{incident_id}/execute`
- **Purpose**: Triggers policy-governed automated retry resolution for an incident.
- **Safety**: Generates a unique idempotency key, executes exponential backoff, verifies downstream state, and resumes order journey.

---

### Category E: Human Approvals (`/approvals`)

#### 1. `GET /api/v1/approvals/pending`
- **Purpose**: Lists all pending operator approval requests for Scenario 3 (HTTP 422 Out-of-Stock).
- **Query Parameters**: `is_demo` (*bool*), `demo_session_id` (*string*).
- **Used by**: View C (Approval Queue Table), Navigation badge counter.

#### 2. `POST /api/v1/approvals/{approval_id}/decide`
- **Purpose**: Submits operator decision (`APPROVED` or `REJECTED`) with required parameters.
- **Request Body**:
  ```json
  {
    "decision": "APPROVED",
    "operator_id": "OP-101",
    "operator_name": "Demo Operator",
    "substitute_sku": "SKU-CYBER-500-ALT",
    "alternate_hub": "HUB-EAST-02",
    "operator_notes": "Authorized substitute stock during hackathon demo"
  }
  ```
- **Validation**: Rejects request with `400 Bad Request` if substitute SKU or warehouse hub is missing or invalid.

---

### Category F: Simulation & Live Demo Controls (`/simulation`)

#### 1. `POST /api/v1/simulation/trigger-scenario`
- **Purpose**: Creates and executes a synthetic order through Scenario 0, 1, 2, 3, or RANDOM.
- **Request Body**:
  ```json
  {
    "scenario_key": "SCENARIO_1_HTTP_503_SELF_HEAL",
    "customer_name": "Sarah Connor",
    "product_sku": "SKU-CYBER-500",
    "total_amount": 299.99,
    "is_demo_order": true,
    "demo_session_id": "demo-1730372400"
  }
  ```
- **Supported `scenario_key` Values**:
  - `SCENARIO_0_CLEAN_RUN`
  - `SCENARIO_1_HTTP_503_SELF_HEAL`
  - `SCENARIO_2_SLA_DELAY`
  - `SCENARIO_3_HARD_REJECTION`
  - `RANDOM` (Applies 50% Clean / 25% 503 / 15% SLA / 10% 422 distribution)

#### 2. `POST /api/v1/simulation/reset-demo-session`
- **Purpose**: Purges **only** orders matching `demo_session_id` and `is_demo_order == True`.
- **Request Body**:
  ```json
  {
    "demo_session_id": "demo-1730372400"
  }
  ```
- **Safety**: Historical records (`demo_session_id == NULL`, `is_demo_order == False`) are mathematically protected.

---

### Category G: Analytics & Health (`/analytics` & `/health`)

#### 1. `GET /api/v1/analytics/metrics`
- **Purpose**: Returns aggregate platform metrics (`total_orders`, `completed_orders`, `self_healed_orders`, `delayed_orders`, `pending_approvals`).
- **Used by**: View A Top Metric Cards.

#### 2. `GET /api/v1/health`
- **Purpose**: Verifies FastAPI server status and SQLite database connectivity.

## 3. How to Test Endpoints in Swagger UI

1. Open [http://localhost:8000/docs](http://localhost:8000/docs) in your browser.
2. Expand the `Simulation Controls` section.
3. Click on `POST /api/v1/simulation/trigger-scenario`.
4. Click **Try it out**.
5. Paste the example JSON payload for Scenario 1 and click **Execute**.
6. Inspect the `200 OK` response payload, verify `order_status: "COMPLETED"`, and verify `resolution.verification_passed: true`.
